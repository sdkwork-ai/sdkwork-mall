# Mall dev preview (local development edge)

Development-only preview of the Adaptive Web PC/H5 bundles:

- URL: `http://mall-dev.birdcoder.com/`
- Desktop browser → PC bundle (`apps/sdkwork-mall-pc/dist/cloud/dev`)
- Mobile browser → H5 bundle (`apps/sdkwork-mall-h5/dist/cloud/dev`)
- API: the cloud bundle resolves `api-dev.birdcoder.com` from the page host
  (`ENVIRONMENT_SPEC.md` §5.1.0.1 host-aware cloud API edge), backed by the
  `development` gateway (`api-dev.*`).

## Build

```bash
pnpm run build:pc:dev:cloud
pnpm run build:h5:dev:cloud
```

## Host edge

`sdkwork-mall` is classified as a client-only module (no owned public
ingress), so this preview runs on the dev host's local-edge nginx, not the
public `sdkwork-webserver` edge. The files in this directory are the
deployed copies:

| File | Role |
| --- | --- |
| `sdkwork-mall-dev.conf` | UA map + `:80`/`:443` server blocks for `mall-dev.birdcoder.com` |
| `sdkwork-mall-dev-static.conf` | PC/H5 static roots, SPA fallback, cache policy |
| `san.ext` | local dev certificate SAN entries (includes `mall-dev.birdcoder.com`) |

Allocation on the dev host (`sdkwork@api-dev.birdcoder.com`):

```text
/home/sdkwork/mall-edge/pc   <- apps/sdkwork-mall-pc/dist/cloud/dev
/home/sdkwork/mall-edge/h5   <- apps/sdkwork-mall-h5/dist/cloud/dev
/home/sdkwork/local-edge/conf/snippets/{sdkwork-mall-dev,sdkwork-mall-dev-static}.conf
```

The edge container mounts the bundles read-only at `/srv/mall`; see
`/home/sdkwork/local-edge/README.md` on the host for the full run command.

## IAM application initialization (development)

Each browser surface is its own IAM tenant application. Bootstrap both against the
development backend before the storefront can sign in or load protected data:

```bash
# PC + H5 templates / tenant applications (bootstrap operator = dev super-admin)
node ../sdkwork-iam/scripts/bootstrap/bootstrap-app.mjs \
  --config apps/sdkwork-mall-pc/agent.app.config.json \
  --backend-base-url http://api-dev.birdcoder.com \
  --tenant-id 100001 --organization-id 0 --environment development \
  --username admin --password "$SDKWORK_IAM_BOOTSTRAP_OPERATOR_PASSWORD" \
  --domain birdcoder.com
# repeat with apps/sdkwork-mall-h5/agent.app.config.json and a distinct --instance-key
```

Rules that matter for a multi-surface workspace:

- The tenant application runtime `appId` MUST equal the manifest
  `backend.appId` (`sdkwork-mall-pc` / `sdkwork-mall-h5`); the public
  application access token generated by `tools/materialize-client-env.mjs` carries
  that id (`IAM_APPLICATION_BOOTSTRAP_SPEC.md` section 4,
  `APP_ACCESS_TOKEN_SPEC.md`).
- Do not let both surfaces default to `instanceKey = dev`: derive it with
  `tenant_application_instance_key(appKey, environment)` (for example
  `sdkwork_mall_pc_dev` / `sdkwork_mall_h5_dev`), otherwise the second
  bootstrap reuses the first tenant application row.
- The surfaces need distinct `primaryDomain` values because
  (tenant, organization, primary domain) is unique in `iam_tenant_application`.

## Credential-entry bootstrap handoff

`nginx.conf` injects the surface's public application access token into the
served `index.html` as the canonical development global:

```text
globalThis.__SDKWORK_CREDENTIAL_ENTRY_BOOTSTRAP_ACCESS_TOKEN__ = "<surface token>"
```

This mirrors `sdkwork-webserver`'s development data-plane injection
(`IAM_CREDENTIAL_ENTRY_SPEC.md` sections 4-5); staging and production must never
inject. Tokens come from the committed `SDKWORK_ACCESS_TOKEN` values in
`apps/*/.env.cloud.development`.

## Known backend gaps (dev gateway 0.1.60)

The storefront no longer calls the retired `catalog/spus` collection. The catalog authority never
published it (it is a second name for `catalog/products`), so no gateway binary could have served
it; the earlier `404 route-not-in-manifest` here was a consumer/contract mismatch, not a stale
gateway build. PC, H5, mini program, and Flutter now read the published
`/app/v3/api/catalog/products` collection, which the catalog app-api route manifest carries and the
gateway composes. Categories, promotions, and login are served by the same gateway.

`shops` answered `503` because the shop capability shipped a UUID-keyed database stub while its
HTTP repository queries the text-keyed `commerce_shop` model: every query failed and the route
envelope reported `50301`. `sdkwork-shop` now ships the matching baseline and a forward migration
(`0002_shop_http_schema_repair`); redeploy the development gateway once so its database-module pass
applies it (or delete/rebuild the development database). No frontend change is involved.
